# Clutcha

[English](README.md) · **中文**

你自己的 agent，跑在自己的电脑上，用手机就能使唤 —— 中间隔着一个读不懂信的邮箱。

Clutcha 由三部分组成，这个仓库是中间那一段。

```
    锦囊AI App  ──信件──▶  邮箱  ──▶  Clutcha Bridge  ──▶  pi 会话
     （手机端）            （只搬运）    （本仓库）           （你的模型）
                ◀──信件──        ◀──
```

| 组成 | 是什么 | 从哪来 |
|---|---|---|
| **锦囊AI App** | 手机端：配对、对话、想看时展开密文。 | App Store，源码不公开 |
| **Clutcha Bridge** | 跑在持有邮箱的那台电脑上的小型 web 应用。拆信、问 agent、封好回答，并让你看见发生了什么。 | **本仓库** |
| **pi 会话** | agent 本身：同一台电脑上的 `pi` 对话，模型、工作目录、工具都在那里定。 | 你自己装的 `pi` |

App 和 bridge 之间从不走网络。它们用双方本来就有的邮箱互寄加密信件，而那个邮箱只能看到密文。

**为什么用邮箱。** 没有端口要开，没有隧道要守，没有服务器要租，互联网上没有任何东西知道 Clutcha 的存在。代价是延迟：一次往返等于一次邮件投递，通常不到一分钟。整个取舍就是这样，而且是故意的。

## Clutcha Bridge

### 它是什么

一个 Python 3 程序，不需要构建，只有两个依赖（`cryptography`、`qrcode`）。它跑在持有邮箱的电脑上，在 `http://127.0.0.1:8787/` 提供一个页面，然后循环做一件事：

```
读邮箱 → 拆信 → 把明文交给 pi → 把回答寄回去
```

其余的一切 —— 三个标签页、配对码、计数器 —— 都是为这个循环服务，或者告诉你它为什么停了。页面支持中英文，切换在右上角，只影响页面，不影响信件内容。

### 你在它上面决定什么

- **设置** —— 邮箱（收件用 POP3 或 IMAP，发件用 SMTP）和承载密文的信件模版。要填的不是登录密码，而是邮箱服务商发的**授权码**，收件发件共用同一份；使用前需要先在邮箱网页端开启 POP3/SMTP 服务。信件卡片里能直接看到"到达时的样子"。
- **会话** —— 手机对话的是哪个 `pi` 会话：会话 ID、工作目录、模型、超时、回复上限、工具。**只有这一个入口**，手机改不了其中任何一项。工作目录默认是 `~/.clutcha-bridge`，首次启动自动创建 —— 这样 agent 一条乱跑的命令改不到正在运行的程序本身。
- **配对** —— 一个二维码，把属于某台手机的密钥交给它。密钥由 bridge 为每台设备单独生成，它从不持有手机的私钥。
- **状态** —— 轮询、收发、错误、运行时长。只用来观察。

bridge 对模型没有意见：`--model` 原样传给 `pi`，本地还是云端一样，留空就是"pi 的默认值"。写错了不会在这里被拦，模型服务端自己的错误会原样返回。思考开关同理：`关闭`，或者什么都不传，交给 `pi` 会话自己的配置。

### 它拒绝做什么

- **只在 `127.0.0.1` 上监听。** 没有密码，因为没有"登录"这回事：它就是你电脑上的一个页面。
- **不让手机打开工具开关。** 工具决定了模型能在那台电脑上做什么，这个开关留在会话页 —— 留在看着这台机器的人手里。邮件翻不动它，已配对设备也不行。
- **不在你注意力之外偷偷查邮箱。** 按轮询周期读信，没有推送，手机端会告诉你上次检查是什么时候。

## 环境要求

| | |
|---|---|
| 电脑 | macOS 12+、Linux 或 Windows 10+ —— bridge 是纯 Python，除下面两个双击脚本外没有平台相关代码 |
| Python | 3.9 或更高 |
| Agent | 已安装 [`pi`](https://github.com/badlogic/pi-mono)，并且能独立回答 |
| 邮箱 | 一个支持 POP3 或 IMAP 以及 SMTP 的账号。最好用专门地址；反正 bridge 的信只有 app 读得懂 |

## 快速开始

**macOS** —— 两个可双击的文件：

```bash
git clone https://github.com/shanleiguang/Clutcha.git
cd Clutcha/bridge
./install.command      # 建 .venv，装两个包
./start.command        # 打开 http://127.0.0.1:8787/
```

**Linux / Windows** —— 同一个程序，手动启动：

```bash
git clone https://github.com/shanleiguang/Clutcha.git
cd Clutcha/bridge
python3 -m venv .venv
.venv/bin/pip install cryptography qrcode      # Windows: .venv\Scripts\pip
.venv/bin/python clutcha_bridge.py             # Windows: .venv\Scripts\python
```

同一份配置只允许一个实例：第二次启动会发现第一个正在跑，于是打开页面而不是报错。端口被占时从 8787 依次退到 8796。

然后：

1. **设置** —— 邮箱地址、授权码，点"测试连接"。邮箱通了，再用 app 扫配对码。
2. **会话** —— 会话 ID、工作目录、模型。不放心就先点"测试会话"跑一次往返。
3. 配对之后直接写信。第一封回信才是真正的验收。

## 邮箱能看到什么

只有密文：

```
-----BEGIN VM MESSAGE-----
Vm1B7kQ…   （base64：版本、nonce、密文、校验标签）
-----END VM MESSAGE-----
```

X25519 协商密钥，HKDF-SHA256 派生，ChaCha20-Poly1305 封装。信封自带版本（`VM1`），armor 标签是固定的（`VM MESSAGE`、`VM CHARACTER`、`VM PAIRING`），KDF 上下文是 `vmessager/v1/{salt,conv,tag}`。

服务商仍然能看到元数据：谁寄给谁、什么时候、多大。这不等于没有泄露，页面上就照实说，不粉饰。

## 控制邮件

有些信不是对话。明文以 `#clutcha:` 开头的，是命令，由 bridge 自己回答 —— 几秒钟，不消耗模型的一轮上下文：

```
#clutcha:ping                        运行时长、模型、工作目录、轮询周期
#clutcha:new                         归档 pi 会话，下一条消息开始新的
#clutcha:config {"poll": {"intervalSeconds": 300}}
```

`config` 会应用轮询和模型相关的设置，逐条回复改了什么，并拒绝邮件不该碰的东西：工具开关、工作目录、会话 ID、邮箱。不带前缀的内容，就是发给 agent 的消息。

## 现状

bridge 是可用的，也是本仓库发布的东西。app 是更顺手的用法；没有 app，bridge 依然是一份完整的协议实现 —— 它的设置页可以自己验证邮箱，所以这两半可以分开上线、分开排查。
